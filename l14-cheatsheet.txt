1. ZENTRALEN SYSLOG-SERVER IN BETRIEB NEHMEN
----------------------------------------------------------------------
  Ausgangslage ansehen:
    Auf SRV-MON:
      systemctl status syslog-ng
      sudo ss -tulpn | grep 514        # noch keine Ausgabe
      ls /etc/syslog-ng/conf.d/

  Empfänger einrichten:
    Auf SRV-MON:
      sudo nano /etc/syslog-ng/conf.d/remote.conf

>>> Anfang
# TechTrade AG - zentraler Syslog-Empfang auf SRV-MON

# Quelle: Meldungen aus dem Netz auf Port 514 (UDP für R1, TCP für SRV-WEB)
# keep-hostname(yes): den Hostnamen aus der Meldung behalten (statt der IP)
source s_remote {
    network(transport("udp") port(514) keep-hostname(yes));
    network(transport("tcp") port(514) keep-hostname(yes));
};

# Filter: Anmelde-Meldungen (Facilities auth und authpriv)
filter f_remote_auth {
    facility(auth, authpriv);
};

# Ziel: eine Datei pro Absender, benannt nach dem Hostnamen
destination d_remote_host {
    file("/var/log/remote/${HOST}.log" create-dirs(yes));
};

# Ziel: alle Anmelde-Meldungen aller Absender in einer Datei
destination d_remote_auth {
    file("/var/log/remote/auth.log" create-dirs(yes));
};

# Verknüpfung: Quelle -> (Filter) -> Ziel
log { source(s_remote); destination(d_remote_host); };
log { source(s_remote); filter(f_remote_auth); destination(d_remote_auth); };
<<< Ende

  Prüfen und neu laden:
    Auf SRV-MON:
      sudo syslog-ng --syntax-only
      # keine Ausgabe = OK; ein Fehler beginnt mit "Error parsing config"
      sudo systemctl restart syslog-ng
      sudo ss -tulpn | grep 514
      # syslog-ng auf udp 514 und tcp 514
  Namen (s_..., f_..., d_...) müssen eindeutig sein. Die Grundkonfiguration
  verwendet schon f_auth und d_auth. Vorhandene Namen anzeigen:
    Auf SRV-MON:
      grep -E "^(source|filter|destination)" /etc/syslog-ng/syslog-ng.conf

  SRV-WEB: rsyslog leitet alle Meldungen ab info per TCP weiter:
    Auf SRV-WEB:
      sudo nano /etc/rsyslog.d/90-srv-mon.conf

>>> Anfang
# TechTrade AG - alle Meldungen ab Severity info per TCP an SRV-MON
# @@ = TCP, @ = UDP
*.info  @@10.10.100.20:514
<<< Ende

    Auf SRV-WEB:
      sudo rsyslogd -N1
      # endet mit "End of config validation run" = OK
      sudo systemctl restart rsyslog

    Auf R1:

2. ALARMREGELN FÜR NETZ UND SHOP ERSTELLEN
----------------------------------------------------------------------
  Regeldatei anlegen:
    Auf SRV-MON:
      sudo nano /etc/prometheus/alerts.yml

>>> Anfang
groups:
  - name: techtrade
    rules:
      - alert: ZielNichtErreichbar
        expr: up == 0
        for: 1m
        labels:
          severity: kritisch
        annotations:
          summary: "{{ $labels.job }} auf {{ $labels.instance }} liefert keine Daten"
          description: "Seit über 1 Minute kein Messwert. Erste Massnahme: Dienst und Erreichbarkeit des Ziels prüfen."

      - alert: ShopNichtVerfuegbar
        expr: probe_success == 0
        for: 1m
        labels:
          severity: kritisch
        annotations:
          summary: "Shop {{ $labels.instance }} nicht verfügbar"
          description: "Prüfung schlägt seit über 1 Minute fehl (HTTP-Status oder Text falsch). Erste Massnahme: nginx auf SRV-WEB prüfen."

      - alert: ShopLangsam
        expr: probe_duration_seconds{job="shop"} > 0.1
        for: 1m
        labels:
          severity: hoch
        annotations:
          summary: "Shop antwortet langsam: {{ $value | humanizeDuration }}"
          description: "Antwortzeit seit über 1 Minute über 100 ms. Erste Massnahme: Auslastung Netz und SRV-WEB prüfen."

      - alert: AuslastungServerSegmentHoch
        expr: rate(ifHCOutOctets{job="snmp", ifName="eth2"}[1m]) * 8 / 100e6 * 100 > 80
        for: 2m
        labels:
          severity: warnung
        annotations:
          summary: "R1 eth2 zum Server-Segment zu {{ $value | printf \"%.0f\" }} % ausgelastet"
          description: "Über 80 % der geplanten 100 Mbit/s seit über 2 Minuten. Erste Massnahme: Verursacher im Dashboard suchen."
<<< Ende

  Regeldatei in prometheus.yml eintragen:
    Auf SRV-MON:
      sudo nano /etc/prometheus/prometheus.yml
  Unter dem Block "alerting:" einfügen, ganz links (0 Leerzeichen):

>>> Anfang
rule_files:
  - /config/alerts.yml
<<< Ende

  Achtung Pfad: Prometheus läuft in einem Container und sieht den Ordner
  /etc/prometheus unter dem Namen /config.

  Prüfen und neu laden:
    Auf SRV-MON:
      sudo docker exec prometheus promtool check rules /config/alerts.yml
      sudo docker exec prometheus promtool check config /config/prometheus.yml
      curl -X POST http://localhost:9090/-/reload
  Ansehen: Prometheus -> Alerts (alle Regeln "Inactive" = OK)

  Alarme per Mail zustellen (Alertmanager):
    Auf SRV-MON:
      sudo nano /etc/alertmanager/alertmanager.yml
  Die Kommentarzeilen oben behalten, alles darunter ersetzen durch:

>>> Anfang
# Mailserver: Mailpit auf SRV-MON (nimmt jede Mail an, ohne Anmeldung)
global:
  smtp_smarthost: 'localhost:1025'
  smtp_from: 'alertmanager@techtrade.lab'
  smtp_require_tls: false

# Alle Alarme an den Betrieb; gleichnamige Alarme in einer Mail bündeln
route:
  receiver: betrieb
  group_by: [alertname]
  group_wait: 30s        # kurz sammeln vor der ersten Mail
  group_interval: 1m     # neue Alarme derselben Gruppe frühestens nach 1 Min
  repeat_interval: 1h    # Erinnerung, solange der Alarm feuert

receivers:
  - name: betrieb
    email_configs:
      - to: 'betrieb@techtrade.lab'
        send_resolved: true   # Entwarnung nach der Behebung
<<< Ende

    Auf SRV-MON:
      sudo docker exec alertmanager amtool check-config /etc/alertmanager/alertmanager.yml
      curl -X POST http://localhost:9093/-/reload
  Ansehen: Alertmanager -> Status (geladene Konfiguration)

  Abfragen hinter den Regeln (Grafana -> Explore -> prometheus):
    up
      Fragt:     Liefert jedes Ziel Daten?   Ergebnis: 1 / 0 pro Ziel.
      Achtung:   Bei shop und shop_tls ist das Ziel der blackbox_exporter
                 auf SRV-MON, nicht nginx. Fällt nginx aus, bleibt up = 1.
    probe_success
      Fragt:     War die letzte Prüfung des Shops erfolgreich?
      Ergebnis:  1 / 0, je eine Zeile für shop und shop_tls.
    probe_duration_seconds{job="shop"}
      Fragt:     Wie lange hat die letzte Prüfung gedauert?
      Ergebnis:  Sekunden, im Normalbetrieb wenige Millisekunden.
    rate(ifHCOutOctets{job="snmp", ifName="eth2"}[1m]) * 8 / 100e6 * 100
      Fragt:     Wie viel Prozent der geplanten 100 Mbit/s schickt R1
                 ins Server-Segment (Mittelwert der letzten Minute)?
      Ergebnis:  0-100 %, ohne Last unter 1 %.

  Zustände in Prometheus -> Alerts:
    Inactive  Bedingung nicht erfüllt
    Pending   Bedingung erfüllt, Mindestdauer (for) noch nicht abgelaufen
    Firing    Bedingung während der ganzen Mindestdauer erfüllt
              -> Prometheus übergibt den Alarm dem Alertmanager -> Mail
  [1m] in rate() ist das Mittelungsfenster (wie wird gerechnet),
  for: 2m die Mindestdauer (wie lange muss es so bleiben).

3. LOGS IN GRAFANA DURCHSUCHEN UND AUF LOGMUSTER ALARMIEREN
----------------------------------------------------------------------
  syslog-ng zusätzlich an Alloy weiterleiten:
    Auf SRV-MON:
      sudo nano /etc/syslog-ng/conf.d/remote.conf
  Am Ende der Datei ergänzen:

>>> Anfang

# Ziel: Weiterleitung an Alloy (RFC 5424 über TCP), Alloy schreibt in Loki
destination d_alloy {
    syslog("127.0.0.1" transport("tcp") port(1514));
};
log { source(s_remote); destination(d_alloy); };
<<< Ende

    Auf SRV-MON:
      sudo syslog-ng --syntax-only
      sudo systemctl restart syslog-ng

  Grafana mit Loki verbinden:
    Firefox -> http://localhost:3000   admin / Gns3456
    Connections -> Data sources -> Add data source -> Loki
    URL: http://localhost:3100   -> ganz unten Save & test

  Logs ansehen: Explore -> Datenquelle Loki -> Code
    {job="syslog"}
      Zeigt: alle Syslog-Meldungen, die über syslog-ng gekommen sind.
    {host="SRV-WEB"}
      Zeigt: nur Meldungen von SRV-WEB.
    {job="syslog", severity="error"}
      Zeigt: nur Meldungen mit Severity err (Label-Wert "error").
    {host="SRV-WEB"} |= "Failed password"
      Zeigt: nur Zeilen, die den Text "Failed password" enthalten.
    {app="nginx"}
      Zeigt: Zugriffe und Fehler des Shops.
    {app="nginx"} |~ "\" 5[0-9]{2} "
      Zeigt: nur Zugriffe mit HTTP-Status 5xx (|~ = regulärer Ausdruck).
    sum by (host) (count_over_time({job="syslog"} |= "Failed password" [5m]))
      Fragt:     Wie viele fehlgeschlagene SSH-Anmeldungen gab es pro Host
                 in den letzten 5 Minuten?
      Ergebnis:  eine Zahl pro Host (eine Linie im Graph).
      Nutzen:    Grundlage für den Logalarm.
    Welche Labels es gibt: im Builder-Modus Feld "Label filters" aufklappen.
    Hinweis: Neue Meldungen erscheinen erst, nachdem syslog-ng neu gestartet
    wurde. Ältere Meldungen stehen nur in den Dateien.

  Logalarme anlegen (beide Regeln in einer Datei):
    Auf SRV-MON:
      sudo nano /etc/loki/rules/fake/logs.yml

>>> Anfang
groups:
  - name: logs
    rules:
      - alert: SSHAnmeldungenFehlgeschlagen
        expr: sum by (host) (count_over_time({job="syslog"} |= "Failed password" [5m])) > 5
        for: 0m
        labels:
          severity: warnung
        annotations:
          summary: "{{ $labels.host }}: mehr als 5 fehlgeschlagene SSH-Anmeldungen in 5 Minuten"
          description: "Möglicher Angriff auf das Passwort. Erste Massnahme: Quell-IP in /var/log/remote/auth.log prüfen."

      - alert: ShopFehlerHTTP5xx
        expr: sum by (host) (count_over_time({app="nginx"} |~ "\" 5[0-9]{2} " [5m])) > 10
        for: 0m
        labels:
          severity: kritisch
        annotations:
          summary: "{{ $labels.host }}: mehr als 10 Shop-Antworten mit HTTP 5xx in 5 Minuten"
          description: "Kunden erhalten Fehlerseiten. Erste Massnahme: letztes Release und /var/log/nginx/error.log prüfen."
<<< Ende

  Texte in LogQL nur in "..." (nicht in '...'). Loki liest Regeldateien
  selbst ein (nach ca. 1 Minute). Prüfen:
    Auf SRV-MON:
      curl -s localhost:3100/loki/api/v1/rules
      # zeigt die Regelgruppe "logs" mit beiden Regeln
      # fehlt eine Regel: Fehler in der Datei, Meldung von Loki ansehen:
      sudo docker logs loki 2>&1 | grep -E "level=(error|warn)" | tail -5
  Ansehen: Grafana -> Alerting -> Alert rules (Quelle logs.yml)

  SSH-Alarm auslösen: zweimal hintereinander je dreimal falsches Passwort:
    Auf SRV-MON:
      ssh test@10.10.20.13
      ssh test@10.10.20.13

4. STÖRUNGEN AUSLÖSEN UND TESTPROTOKOLL FÜHREN
----------------------------------------------------------------------
  Beobachten: Prometheus -> Alerts (Zustand), Mailpit (Mails mit Zeit).
  Uhrzeit für das Protokoll:  date +%T

  Störung Antwortzeit: Verzögerung auf SRV-WEB
    Auf SRV-WEB:
      sudo tc qdisc add dev ens3 root netem delay 200ms
      tc qdisc show dev ens3          # zeigt "netem ... delay 200ms"
    Zurücksetzen:
    Auf SRV-WEB:
      sudo tc qdisc del dev ens3 root

  Störung Auslastung: Last ins Server-Segment (90 Mbit/s während 5 Min)
    Auf SRV-MON:
      iperf3 -c 10.10.20.13 -b 90M -t 300
    Zurücksetzen: Strg+C oder Ende abwarten.

  Störung Engpass: R1 eth2 auf 20 Mbit/s drosseln, dann Last erzeugen
    Auf R1:
      configure
      set qos policy shaper ENGPASS bandwidth 20mbit
      set qos policy shaper ENGPASS default bandwidth 100%
      set qos policy shaper ENGPASS default queue-type drop-tail
      set qos interface eth2 egress ENGPASS
      commit
      exit
    Auf SRV-MON:
      iperf3 -c 10.10.20.13 -t 300
      # iperf3 zeigt etwa 19 Mbit/s; etwa 94 Mbit/s = Drosselung nicht aktiv
    Zurücksetzen:
    Auf R1:
      configure
      delete qos interface eth2
      delete qos policy shaper ENGPASS
      commit
      exit
    (kein save nötig: die Drosselung soll nicht dauerhaft bleiben)

  Störung Ausfall Shop:
    Auf SRV-WEB:
      sudo systemctl stop nginx
    Zurücksetzen:
    Auf SRV-WEB:
      sudo systemctl start nginx

  Ausgangszustand prüfen nach jedem Test:
    Auf SRV-WEB:
      tc qdisc show dev ens3          # kein netem
      systemctl is-active nginx       # active
    Auf R1:
      show configuration commands | match qos   # keine Ausgabe
    Prometheus -> Alerts: alles Inactive

  Weshalb nur eine Mail?  Der Alertmanager bündelt gleichnamige Alarme
  (group_by: [alertname]) und wiederholt eine Mail erst nach
  repeat_interval (1h). Nach der Behebung folgt genau eine Entwarnung.

----------------------------------------------------------------------
5. ÜBERWACHUNG SICHERSTELLEN
----------------------------------------------------------------------
  Ausfall eines Exporters:
    Auf SRV-WEB:
      sudo systemctl stop prometheus-node-exporter
    Ansehen: Prometheus -> Status -> Target health (node DOWN),
             Alerts: ZielNichtErreichbar, Mail in Mailpit
    Zurücksetzen:
    Auf SRV-WEB:
      sudo systemctl start prometheus-node-exporter

  Wartungsfenster (Silence):
    Alertmanager http://localhost:9093 -> New Silence
    Matcher: alertname="ShopNichtVerfuegbar"   Duration: 15m
    (Wert in Anführungszeichen, dann + oder Enter: Matcher erscheint als Chip)
    Creator und Comment (Grund) ausfüllen -> Create
    Dann nginx stoppen: Alarm erscheint in Prometheus als Firing,
    aber es kommt keine Mail. Im Alertmanager sind stummgeschaltete
    Alarme nur mit dem Häkchen "Silenced" sichtbar.
    Danach nginx starten, Silence beenden (Silences -> Expire).
    Zeiten im Alertmanager sind in UTC (Schweiz: UTC+1, Sommer UTC+2).
