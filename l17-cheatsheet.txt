RUNDE 1 · RED TEAM: AUFKLÄRUNG
---------------------------------------------------------------------

Was ist von aussen erreichbar?
Auf KALI:
nmap -sV 10.10.20.13
nmap -sV 10.10.100.20
# -sV = Versionserkennung: Nmap fragt die Dienste nach ihrer Kennung
# Spalten: PORT, STATE (open = erreichbar), SERVICE, VERSION
# Ohne weitere Angabe prüft Nmap nur die 1000 häufigsten Ports.
# Meldung "Unable to determine any DNS servers" ist harmlos (KALI braucht kein DNS)
# Die Spalte SERVICE ist oft nur eine Vermutung anhand der Portnummer
# (erkennbar am "?", z. B. "jetdirect?" auf Port 9100). Welches Programm
# wirklich dahintersteht, zeigt erst "sudo ss -tlnp" auf dem Server.

Was verrät der Webserver über sich?
Auf KALI:
curl -I http://10.10.20.13
curl -k -I https://10.10.20.13
# -I = nur die Kopfzeilen der Antwort anzeigen (Header)
# -k = selbstsigniertes Zertifikat akzeptieren
# Zeile "Server:" = Software und Version des Webservers
# Statuszeile "501 Unsupported method" ist normal: Die Shop-App beantwortet
#   nur ganze Anfragen, keine reinen Header-Abfragen. Massgebend ist "Server:".

RUNDE 2 · BLUE TEAM: LAGE BEURTEILEN
---------------------------------------------------------------------

Welche Programme stehen hinter den erreichbaren Ports?
Auf SRV-WEB:
sudo ss -tlnp
# ss = Netzwerkverbindungen anzeigen
# -t = TCP, -l = nur wartende Ports (listen), -n = Zahlen statt Namen,
# -p = zugehöriges Programm (Spalte Process)
# Spalte "Local Address:Port":
#   0.0.0.0:<port>, *:<port>, [::]:<port> = auf allen Adressen -> von anderen Systemen erreichbar
#   127.0.0.x:<port>, [::1]:<port>        = nur lokal erreichbar
# docker-proxy = Port eines Containers, den Docker nach aussen veröffentlicht

Welche Container laufen?
Auf SRV-WEB:
sudo docker ps
# Spalte IMAGE: Image und Version (Tag nach dem Doppelpunkt)
# Spalte PORTS: veröffentlichte Ports, z. B. 0.0.0.0:443->443/tcp
# Spalte NAMES: Name des Containers
# Software in Containern kennt die Paketverwaltung des Servers (apt) nicht

Pakete von SRV-WEB auf Schwachstellen prüfen
Auf SRV-WEB:
sudo trivy rootfs --skip-db-update --scanners vuln --pkg-types os --severity HIGH,CRITICAL --ignore-unfixed / | grep Total
# rootfs /          = das Dateisystem des Servers prüfen
# --skip-db-update  = Datenbank nicht herunterladen: im Lab wegen der langsamen
#                     Internetverbindung (Datenbank ca. 60-80 MB). Im Betrieb immer
#                     die aktuelle Datenbank verwenden (Standard ohne diese Option).
# --scanners vuln   = nur Schwachstellen
# --pkg-types os    = nur Pakete des Betriebssystems (apt), keine Container-Daten
# --severity        = nur hohe und kritische Befunde
# --ignore-unfixed  = nur Befunde, für die es bereits eine korrigierte Version gibt
# | grep Total      = nur die Zusammenfassung: Anzahl je Schweregrad
# Die Liste ist lang (grösster Teil: Linux-Kernel). Niemand liest sie ganz.
# Man prüft gezielt die Pakete der Dienste, die von aussen erreichbar sind:
#   Port 22    sshd            -> Paket openssh
#   Port 9100  prometheus-node -> Paket prometheus-node-exporter
#   Port 10050 zabbix_agent2   -> Paket zabbix-agent2
#   Port 5201  iperf3          -> Paket iperf3
sudo trivy rootfs --skip-db-update --scanners vuln --pkg-types os --ignore-unfixed / | grep -i -A 2 openssh
sudo trivy rootfs --skip-db-update --scanners vuln --pkg-types os --ignore-unfixed / | grep -i -A 2 node-exporter
sudo trivy rootfs --skip-db-update --scanners vuln --pkg-types os --ignore-unfixed / | grep -i -A 2 zabbix
sudo trivy rootfs --skip-db-update --scanners vuln --pkg-types os --ignore-unfixed / | grep -i -A 2 iperf3
# grep -i -A 2 <name> = Zeilen mit dem Namen plus 2 Folgezeilen; keine Ausgabe = kein Befund
# Spalten: Paket, CVE, Schweregrad, installierte Version, korrigierte Version, Titel
# Ports 80 und 443 (nginx) laufen im Container -> Prüfung der Images
# SRV-MON prüfen wir in diesem Lab nicht mit Trivy (Umfang). Auch nicht
# erreichbare Systeme werden gepatcht: Wer SRV-WEB übernimmt, erreicht von dort
# aus auch interne Systeme. Die Erreichbarkeit bestimmt die Dringlichkeit,
# nicht, ob gepatcht wird. Für die offenen Dienste auf SRV-MON ist die
# Sofortmassnahme die Zugriffsregel auf R1, das Patchen läuft im regulären Zyklus.

Images des Shop-Stacks prüfen
Auf SRV-WEB:
sudo trivy image --skip-db-update --scanners vuln nginx:1.30.5-alpine | grep Total
sudo trivy image --skip-db-update --scanners vuln postgres:16.15-alpine | grep Total
sudo trivy image --skip-db-update --scanners vuln techtrade/shop:1.4 | grep Total
# nginx ist von aussen erreichbar (Ports 80, 443) -> gezielt prüfen:
sudo trivy image --skip-db-update --scanners vuln --ignore-unfixed nginx:1.30.5-alpine | grep -i -A 2 nginx
# keine Ausgabe = Trivy kennt keinen Befund zu nginx selbst
# (Befunde zu anderen Paketen im Image können trotzdem bestehen)

Meldungen abgleichen: Versionen gezielt nachschlagen
Auf SRV-WEB:
apt policy openssh-server
# Installed = installierte Version, Candidate = neueste verfügbare Version
apt changelog openssh-server 2>/dev/null | grep -m 1 -B 10 CVE-2024-6387
# zeigt, in welcher Paketversion Ubuntu die Lücke behoben hat:
# massgebend ist die Zeile "openssh (<version>) noble-security" direkt über dem Eintrag
# 2>/dev/null = Hinweise von apt ausblenden; -B 10 = 10 Zeilen vor dem Treffer
# (Ubuntu übernimmt Korrekturen in ältere Versionen = Backport)
sudo docker exec shop-proxy-1 nginx -v
sudo docker exec shop-db-1 postgres --version
# Version der Software im jeweiligen Container
sudo docker port shop-db-1
# keine Ausgabe = Datenbank ist nicht nach aussen veröffentlicht

Auf R1:
show version
show configuration commands | match service
# alle aktiven Dienste auf R1 (z. B. ssh, https)

RUNDE 3 · BLUE TEAM GEGEN RED TEAM: ANGRIFFE ERKENNEN
---------------------------------------------------------------------

Blue Team: HOME_NET setzen
Auf SRV-WEB:
sudo nano /etc/suricata/suricata.yaml
# Zeile HOME_NET im Abschnitt vars: address-groups: anpassen auf
#   HOME_NET: "[10.10.0.0/16]"
# EXTERNAL_NET: "!$HOME_NET" bleibt (alles ausser HOME_NET)
sudo suricata -T -c /etc/suricata/suricata.yaml
# -T = nur Konfiguration testen, Suricata nicht starten
# erwartet: "Configuration provided was successfully loaded"

Blue Team: Regeln laden
Auf SRV-WEB:
sudo suricata-update
# lädt den Regelsatz Emerging Threats Open nach /var/lib/suricata/rules/
sudo systemctl restart suricata
sudo systemctl status suricata --no-pager
sudo tail -n 5 /var/log/suricata/suricata.log
# letzte Zeile «Engine started» = bereit. Erst dann angreifen (Start dauert einige Sekunden)
# Zeile «detect: … signatures processed» = Anzahl aktiver Regeln

Blue Team: Alarme live mitlesen (zweites Terminal offen lassen)
Auf SRV-WEB:
sudo tail -f /var/log/suricata/fast.log
# fast.log = eine Zeile pro Alarm: Zeit, Signatur, Priorität, Protokoll, Quelle -> Ziel
# tail -f = neue Zeilen laufend anzeigen, beenden mit Ctrl+C

Red Team: Angriff
Auf KALI:
nmap -sV 10.10.20.13
nmap -sV 10.10.100.20

for i in 1 2 3 4 5 6 7 8; do sshpass -p falsch ssh -o StrictHostKeyChecking=no -o PubkeyAuthentication=no admin@10.10.20.13 exit; done
# 8 Anmeldeversuche mit falschem Passwort (Benutzer admin)
# sshpass -p = Passwort übergeben (hier absichtlich falsch)

curl -k -I https://10.10.20.13

Blue Team: Auswertung
Auf SRV-WEB:
sudo cat /var/log/suricata/fast.log
# alle Alarme seit dem Start

Blue Team: Systemlog der SSH-Anmeldungen
Auf SRV-WEB:
sudo journalctl -u ssh --since "15 min ago" | grep -i -E "failed|invalid"
# -u ssh = nur Meldungen des SSH-Dienstes
# grep -E "failed|invalid" = Zeilen mit failed oder invalid

RUNDE 4 · BLUE TEAM HÄRTET, RED TEAM GREIFT ERNEUT AN
---------------------------------------------------------------------

M1 Behebung - nur OpenSSH aktualisieren
Auf SRV-WEB:
apt policy openssh-server
# Zustand vorher festhalten
sudo apt update
sudo apt install --only-upgrade openssh-server
# --only-upgrade = nur aktualisieren, nichts neu installieren
# apt aktualisiert openssh-client und openssh-sftp-server mit,
# weil openssh-server genau dieselbe Version davon verlangt
apt policy openssh-server
# Installed muss mindestens der Version aus Meldung A-01 entsprechen
# Achtung: Versionen sind keine Dezimalzahlen. 13.20 ist NEUER als 13.3 (20 > 3).
dpkg --compare-versions 1:9.6p1-3ubuntu13.20 ge 1:9.6p1-3ubuntu13.3 && echo ja
# ja = installierte Version ist mindestens so neu wie die korrigierte

M4 Behebung - Image des Reverse Proxy ersetzen
Auf SRV-WEB:
sudo docker exec shop-proxy-1 nginx -v
# Zustand vorher festhalten
cd /opt/shop
sudo nano compose.yaml
# beim Reverse Proxy: image: nginx:1.30.6-alpine
sudo docker compose pull proxy
# nur das Image des Dienstes «proxy» holen. Ohne Dienstnamen versucht Docker
# alle Images zu holen und scheitert am Shop-Image (lokal gebaut, nicht auf Docker Hub)
sudo docker compose up -d proxy
# startet nur den Container des Reverse Proxy mit dem neuen Image neu
sudo docker exec shop-proxy-1 nginx -v
curl -k -I https://10.10.20.13
sudo trivy image --skip-db-update --scanners vuln --ignore-unfixed nginx:1.30.6-alpine
# kurze Liste: nur Befunde mit Korrektur; zu nginx selbst darf keiner mehr erscheinen
# Im Container wird nicht gepatcht: neues Image, neuer Container

M2 Erkennung - eigene Suricata-Regel
Auf SRV-WEB:
sudo nano /etc/suricata/rules/local.rules
# folgende Zeile in die Datei einfügen (eine Zeile), speichern:
alert ip 203.0.113.66 any -> $HOME_NET any (msg:"A-06 Verkehr von bekannter Angriffsadresse aus Threat-Feed"; sid:1000001; rev:1;)
# alert             = melden (nicht blockieren)
# ip                = jeder IP-Verkehr (TCP, UDP, ICMP)
# 203.0.113.66 any  = Quelle: Adresse aus A-06, beliebiger Port
# ->                = Richtung: von der Quelle zum Ziel
# $HOME_NET any     = Ziel: Netze der TechTrade AG, beliebiger Port
# msg               = Alarmtext mit Verweis auf A-06 (dafür grep A-06)
# sid               = Signatur-ID; eigene Regeln ab 1000000
# rev               = Version der Regel, bei jeder Änderung +1
sudo suricata -T -c /etc/suricata/suricata.yaml
sudo systemctl restart suricata
Auf KALI (Regel auslösen):
curl -k -I https://10.10.20.13
Auf SRV-WEB:
sudo grep A-06 /var/log/suricata/fast.log
# Alarme der eigenen Regel (sofern "A-06" in msg steht)

M3 Verhinderung - Firewall auf R1
Auf R1:
configure
# Regeln im Weiterleitungsfilter (Verkehr, der durch R1 hindurch geht).
# Platzhalter in <> ersetzen. Reihenfolge: zuerst erlauben, dann verwerfen.
set firewall ipv4 forward filter rule 20 action accept
set firewall ipv4 forward filter rule 20 inbound-interface name <schnittstelle zum netz extern>
set firewall ipv4 forward filter rule 20 destination address <adresse SRV-WEB>
set firewall ipv4 forward filter rule 20 protocol tcp
set firewall ipv4 forward filter rule 20 destination port <ports, durch komma getrennt>
set firewall ipv4 forward filter rule 30 action drop
set firewall ipv4 forward filter rule 30 inbound-interface name <schnittstelle zum netz extern>
set firewall ipv4 forward filter rule 30 destination address <netze der TechTrade AG>
compare
# zeigt die Änderungen vor dem Übernehmen
commit
save
exit
show firewall ipv4 forward filter
# Regeln mit Zählern (Pakete, Bytes) je Regel

Prüfen: Verwaltung aus dem Management-Netz geht weiter
Auf SRV-MON:
ssh gns3@10.10.20.13 hostname
# erwartet: Passwortabfrage, danach SRV-WEB

Red Team: erneuter Angriff
Auf KALI:
nmap -sV 10.10.20.13
nmap -sV 10.10.100.20
# erwartet: SRV-WEB nur noch 80 und 443
# SRV-MON: "Host seems down" - R1 verwirft auch den Ping von Nmap.
# Gegenprobe ohne Ping: nmap -Pn 10.10.100.20 -> alle Ports "filtered"
for i in 1 2 3; do sshpass -p falsch ssh -o ConnectTimeout=5 -o StrictHostKeyChecking=no admin@10.10.20.13 exit; done
# erwartet: Zeitüberschreitung (timed out) statt Passwortabfrage
curl -k -I https://10.10.20.13
# erwartet: Shop antwortet weiterhin
Auf R1:
show firewall ipv4 forward filter
# Zähler von Regel 30 sind gestiegen = Pakete von KALI wurden verworfen
